# Thorium Library and Reader accessibility audit

Date: 19 October 2026. Source revision: `0cd77ab84e5033f51b446e55c8ef03af00884930`.
Application: `3.5.2-beta.1`; Windows; development build.

**Result:** the tested interfaces have confirmed WCAG A/AA defects and cannot receive a passing conformance finding. The highest priorities are unnamed Reader controls/editors, unnamed Library actions, missing document language, malformed navigation semantics, and clipped settings at zoom. This is an engineering audit of the available states, not a certification of every conditional application flow.

## Scope and interpretation

Baseline: [WCAG 2.2 Level A and AA](https://www.w3.org/TR/WCAG22/), interpreted for desktop software using [WCAG2ICT](https://www.w3.org/TR/wcag2ict-22/). WCAG conformance applies to complete interfaces and processes; a component check does not establish application conformance. Automated passes do not establish conformance either.

Work proceeds in two phases: static component/stylesheet review, followed by the running Electron application started with `npm run start:dev:quick`. No application source fixes are included. The continuation also builds separate audit-only Library and Reader component fixtures, inheriting each renderer's loaders and runtime scope checker. They introduce no direct imports between application runtime islands.

The component matrix covers Thorium-owned React components in shared renderer, Library and Reader code. PDF webview, EPUB publication content, Divina and audiobook surfaces require additional format-specific runtime evidence. Third-party publication accessibility is distinct from the accessibility of Thorium's controls. Source inventories describe potential UI, including conditional branches; they are not proof that every branch was rendered.

Statuses: **S** = source-confirmed defect; **D** = dynamically reproduced; **R** = risk requiring further evidence; **U** = untested; **cleared** = suspected issue disproved for the tested case. Severity is impact/priority, not a WCAG conformance level. Best-practice findings are distinguished from success-criterion failures.

## Positive source observations

- Shared Dialog/AlertDialog use React Aria modal and dialog primitives; stable title/description IDs are supplied by context. Cancel requests initial focus for confirmation dialogs. Verify focus containment/restoration in runtime rather than assuming the library guarantees all application compositions.
- Tabs explicitly configure vertical orientation in Library settings, Reader settings and Reader navigation. Shared RadioGroup and radio wrappers support group labels, native selection state and disabled states.
- Many icon buttons have useful localized aria-label or title. A title can supply an accessible name; title-only controls are not automatically counted as unnamed.
- Native checkboxes hidden with `.checkbox_custom_input { display:none }` are replaced with named, focusable ARIA checkboxes and Space handlers. This is not automatically a duplicate-control defect; state synchronization and visible focus still need testing.
- Skip controls target programmatically focusable toolbar/content anchors. Reader navigation headings use aria-level. Publication metadata frequently marks language and text direction.
- Image viewer includes keyboard reachable zoom buttons and preserves source image alternatives. PDF annotation overlay is explicitly passive and aria-hidden; annotation access must be assessed through Reader panels.

- Library settings trapped Tab through a full cycle; vertical arrow keys selected Profiles, Storage and Advanced; Escape returned focus to the Settings trigger. Focus trace is saved in `library-focus-settings-general.json`.
- Custom template checkbox responded to Space and exposed its updated checked state. Labelled comboboxes exposed suggestions, selection and expansion. Theme was restored to Automatic and application zoom to 100%.
- Reader modal settings contained keyboard focus through spacing controls; the docked selector had a visible parent outline. Docking was exercised in modal and right-docked modes. No screen reader listening test is implied.
- Bookmark/annotation popovers and print configuration opened and could be cancelled. No note, bookmark or print job was saved. The remote progression alert initially focused its safe Cancel action; cancellation preserved the local location.
- Local OPDS card click was verified in source to open publication information. The information dialog exposed named acquisition controls and a status for reading progress. No acquisition, loan or account action was submitted. An initial automatic approval rejection was resolved by verifying the exact dialog trigger and retrying that same inspection action.
- The tested dark-theme settings scan had no automatic color-contrast violations. Home scans retain contrast manual-review items; there is no blanket contrast pass for all themes or publication content.

### Advisories and unresolved evidence

Heading-level jumps, main nested within a region, region coverage, missing main/H1 inside an isolated popover, and presentation-role-conflict are retained in raw axe results. They need semantic interpretation; they are not all separate WCAG failures. In particular, missing main/H1 in a modal-only scan is not an instruction to add a main landmark to every dialog.

PDF print range has a visible `<label for=print-range>` but the input only has name=print-range and no matching ID (`Print.tsx:202,208`). Its title “Pages” provides an accessible name, so this is a label-association advisory rather than an unnamed-control failure. Fix the ID association. Clickable cover images also mix presentation role and focusability (`Cover.tsx:139`); prefer a named action around an informative/decorative image as appropriate.

The sample EPUB resource has lang=en and an accessible text tree. Its scan flags publication-owned inline link contrast and structural best practices; this is not a verdict on the entire EPUB or Thorium shell. The tested PDF webview flags missing language, duplicate landmark names, viewport scaling restrictions, and contrast requiring manual review. PDF text, tagging, reading order and full-document accessibility remain separate checks.

Native Windows UIA capture timed out waiting for application approval. The runtime evidence instead uses Electron CDP, axe, Chromium accessibility trees/ARIA snapshots, actual dispatched keyboard events, computed styles and screenshots. NVDA/JAWS, native menus/file pickers, and end-to-end Windows accessibility API integration remain untested. Playwright ARIA snapshots can omit title-derived names that Chromium exposes: the grid-filter snapshot displays a nameless dialog, but [its native Chromium AX evidence](evidence/library-grid-filter-ax.json) confirms the name “Add filters”. Ambiguous name findings must be checked in the Chromium tree.

## Coverage and remaining conformance work

See the [component matrix](component-matrix.csv), [55-criterion checklist](wcag-criteria.csv), [application state results](state-results.csv), [fixture state results](fixture-state-results.csv), [47-file continuation](continuation-47.csv) and [structural evidence](evidence/static-inventory.json). “Structural review” means the JSX AST was inventoried and control patterns inspected. Components with no recorded issue are **not certified conformant**. The previous 47 unexercised entries now have explicit dispositions: 41 rendered in fixtures, three traced composed helpers, and three inactive source files. Thus **145 of 148 files have representative runtime or composed evidence; three have no active UI implementation**. The matrix distinguishes application, application+fixture, component-fixture, composed and inactive coverage, and records per-file observations and limitations. A file with runtime evidence may still have untested branches.

Every interactive surface still needs the applicable checks for names/roles/states, keyboard access, logical focus, visible/unobscured focus, dialog dismissal/restoration, errors/status feedback, text and non-text contrast, 200% text resizing, reflow equivalent to 320 CSS px, text-spacing overrides, and minimum target size/spacing. Color themes, hover/focus/disabled/selected/error/empty/loading states and small windows must be covered, not only default screenshots.

Publication/format matrix: reflowable EPUB, fixed layout EPUB, tagged and untagged PDF, Divina/comics, audiobook and media overlays; RTL and mixed-language content; LCP password/error/renew/return flows; OPDS browse/search/pagination/borrow/hold/account flows. Account and lending end-to-end checks require suitable fixtures and access. The continuation covers local presentation/pending/error contracts for several such components, without establishing the real service process. Destructive actions are inspected without confirming deletion or loan changes.

Manual assistive technology work remains necessary: NVDA or JAWS with Windows UIA, browse/focus modes, reading order and announcements inside EPUB/PDF webviews, speech/voice control, Windows high contrast, OS scaling and magnification. An accessibility-tree inspection is not a screen reader listening test.

Media criteria (captions, audio descriptions, alternatives), authentication (including 3.3.8), time limits and flashing/movement must be assessed against relevant content and flows. No application-wide “not applicable” judgement is made simply because those features were not exercised.

Recommended repair order: label/name the exposed controls and editors; set host language; repair list/heading/nested-control semantics and docked panel references; fix modal sizing/reflow; then repeat keyboard, zoom, contrast and native AT checks across the remaining flows. These are audit recommendations; no product source was changed.

```powershell
node scripts/accessibility/static-audit.cjs docs/accessibility/evidence/static-inventory.json
npm run start:dev:quick
# In another terminal while Electron's debug port 9223 is available:
node scripts/accessibility/snapshot.cjs library-home
node scripts/accessibility/webviews.cjs publication-webview
# Separate component fixtures (isolated userData; debug port 9224):
node scripts/accessibility/fixture-build.cjs
node_modules/.bin/electron.cmd scripts/accessibility/fixture-main.cjs
# In another terminal while the fixture process runs:
node scripts/accessibility/fixture-scan.cjs
node scripts/accessibility/fixture-interactions.cjs
node scripts/accessibility/fixture-additional.cjs
# Regenerate report indexes from captured evidence:
node scripts/accessibility/continuation-summary.cjs
node scripts/accessibility/component-matrix.cjs
node scripts/accessibility/summarize.cjs
```

Snapshot script attaches to the existing Electron debug endpoint, runs axe with WCAG 2.0/2.1 A/AA, WCAG 2.2 AA and best-practice tags, saves violations, manual-review items, rule pass counts, screenshots and ARIA snapshots, then disconnects. It does not assert that every axe result is a confirmed WCAG failure. It only scans Library/Reader host pages; webviews require separate inspection.

The built-in Reader `AXE_A11Y` IPC action removes `publication_viewport` before running its React checker (`index_reader.ts:99–136`). Do not use that action to establish accessibility of the actual Reader-plus-publication experience. This audit injects axe into the intact host instead.
