# PDF Annotations Changelog

This changelog tracks project decisions, actions, scope changes, and documentation updates for PDF annotations.

It is not a product release changelog. Product-facing release notes should be written separately when the feature ships.

Use newest entries first. Prefer concrete dates and short bullets.

Agent maintenance rule: any agent that changes project decisions, scope, actions, TODOs, or implementation-facing documentation must add a same-day entry here in the same turn.

Decision enforcement: every project choice or scope decision must include the "why". A valid decision entry states the choice, the reason for it, the constraint or policy behind it, and any meaningful alternative that was rejected or deferred.

Technical decision enforcement: every technical or algorithmic choice must be demonstrated and critiqued. A valid entry includes context, decision, demonstration, critique, alternatives, and a revisit trigger.

Entry tags:

- `Decision` - a durable project choice.
- `Action` - a concrete change made in the repository or project docs.
- `Scope` - something explicitly included or excluded.
- `Follow-up` - work intentionally deferred.

- Decision: Validate PDF annotation drafts at the host boundary before creating Thorium notes. Why: event-bus payloads are runtime data, so TypeScript cannot prove that `page`, `rects`, `type`, or `quote` remain valid when they cross from PDF.js webview code into host persistence. Demonstration: `validatePdfAnnotationDraft()` accepts only `pdf-text-highlight`, 1-based integer pages, non-empty finite non-zero rects, and optional string quotes; host tests prove invalid drafts do not call persistence, and validation tests prove accepted rects are defensively copied. Critique: this hardens creation drafts only; `annotations:sync` still has minimal shape validation plus id guards rather than a full schema for every transported field. Alternatives rejected or deferred: trusting TypeScript event types would not protect runtime IPC/bus data; validating only inside the webview would miss malformed host-bound payloads; adding a schema library is deferred until more transport payloads require shared schema tooling. Revisit trigger: revisit when PDF annotation transport expands for export/import, native PDF exchange, or bulk/runtime sync validation.
- Decision: Cover Reader-level PDF annotation behavior through small helpers consumed by `Reader.tsx` and `ReaderMenu.tsx`, rather than mounting the full connected React reader. Why: the current repository has no established React component test harness, and mounting the connected reader would pull in Redux, Electron-adjacent imports, translations, Radix popovers, and unrelated UI state. Demonstration: `Reader.tsx` now uses `getPdfAnnotationCreatePresentation()`, `buildPdfAnnotationDraftEditorTransport()`, and `getPdfAnnotationVisibilityPayload()`; `ReaderMenu.tsx` uses `compareAnnotationPanelProgression()`; Jest proves explicit creation opens the draft editor path, instant/quick creation persists silently, invalid sources are rejected, hide maps only to overlay visibility, and progression sorting delegates PDF visual order before EPUB progression fallback. Critique: this still does not assert rendered React DOM or focus behavior in `ReaderHeader`; it proves the decision model wired into the components. Alternatives rejected or deferred: adding React Testing Library only for this slice would expand the test stack; testing private class methods directly would be brittle; leaving these decisions covered only by manual review already allowed regressions to slip through. Revisit trigger: revisit when the project adopts a standard React component test harness or splits Reader/Header/Menu into smaller presentational components.
- Decision: Split the standalone harness into independent Playwright scenarios instead of one long chained smoke test. Why: the previous test proved the happy path but made failures hard to diagnose and allowed an early failure to hide later coverage. Demonstration: the harness now runs six named tests for invalid selection, click selection, hide, zoom/rotation/style/navigation, deletion, and instant mode; the command reports each scenario separately and all six pass. Critique: the suite reopens the harness for each scenario, so it is slightly more repetitive and may take longer as browser coverage grows. Alternatives rejected or deferred: keeping one chained test was compact but weak diagnostically; introducing shared browser state between scenarios would be faster but could reintroduce hidden coupling; Electron runtime tests remain deferred. Revisit trigger: revisit if Playwright runtime becomes too slow or if a future Electron harness replaces the standalone browser harness.
- Decision: Reject PDF annotation create requests that include a draft but omit or falsify `source`. Why: `source` controls the user flow boundary between explicit creation, instant creation, and quick/no-editor creation; accepting an unknown source would make editor behavior ambiguous and could persist notes from malformed runtime messages. Demonstration: `createPdfAnnotationNoteDraft()` now checks `source` before draft conversion, logs `annotation:create-requested ignored invalid source` with the bad value, and returns without persistence; `pdfAnnotationHost.test.ts` proves unknown and missing sources do not call persistence or sync. Critique: the check is intentionally a small allowlist rather than a full event-schema validator, so other host-bound payloads still rely on their local guards. Alternatives rejected or deferred: defaulting unknown sources to explicit creation could open the editor unexpectedly; defaulting to instant creation could silently persist bad messages; validating only in the webview would not protect the host boundary. Revisit trigger: revisit when PDF annotation bus payloads move to a shared runtime schema.
- Decision: Sort PDF annotation panel progression by visual reading order instead of raw PDF `y1` ascending. Why: PDF.js viewport conversion stores PDF-space coordinates where larger `y` values are nearer the visual top on unrotated pages, so raw ascending vertical sort can place lower highlights before upper highlights. Demonstration: `comparePdfAnnotationsByPagePosition()` now sorts page ascending, `max(y1, y2)` descending, `min(x1, x2)` ascending, then id; `pdfAnnotationPanel.test.ts` proves an upper highlight sorts before a lower one and leftmost highlights sort first on the same visual line. Critique: this is still a first-rectangle reading-order heuristic; complex multi-column PDFs, rotated content, and multi-rect spans may eventually need page text-layer ordering or a richer comparator. Alternatives rejected or deferred: sorting by raw `y1` ascending contradicted visual order; sorting only by creation date would ignore document position; deriving full text-layer order is deferred until real PDFs expose failures. Revisit trigger: revisit when multi-column, rotated-page, or multi-rect reading-order QA reveals misordered annotations.
- Decision: Keep the PDF hide option as overlay visibility only, not an annotation panel filter. Why: `hide` is a display preference for rendered marks in the PDF webview, while the annotation panel is the management surface for existing Thorium notes. Demonstration: `Reader.tsx` continues to send only `annotations:set-visibility`; the webview removes/restores overlays without deleting snapshots, and the docs now state that panel cards remain listed while hidden. Critique: panel navigation can still target a hidden overlay and therefore may scroll without a visible flash, which may need clearer UX copy later. Alternatives rejected or deferred: filtering panel cards would make hidden annotations harder to manage; sending an empty snapshot would erase webview state; deleting notes would conflate visibility with persistence. Revisit trigger: revisit only if product explicitly redefines hide as a panel filter.
- Decision: Emit `annotation:selection-error` instead of silently ignoring failed selection capture. Why: users and QA need a host-visible signal when annotation creation cannot produce a valid draft, but this tranche should not introduce a finalized toast UX or new lifecycle bus. Demonstration: `selectionToDraft()` now maps strict rejection points to typed reasons, `Reader.tsx` logs the diagnostic and leaves a toast integration point, Jest verifies every reason, and the harness verifies a controlled invalid selection creates no annotation while logging the typed event. Critique: the event is useful plumbing, but it is not yet localized user feedback; true cross-page browser selection automation also remains deferred because it needs deterministic sample text-layer geometry. Alternatives rejected or deferred: keeping silent rejection would hide failures; creating invalid partial annotations would corrupt the persisted one-page target model; adding final toast microcopy now would force product copy and translations before the UX is designed. Revisit trigger: revisit when localized selection-error feedback, true cross-page targets, or accessibility-specific creation flows enter scope.
- Decision: Use one static toast message for PDF annotation validation failures in this tranche. Why: the user needs immediate visible feedback when annotation creation validation fails, while final product microcopy and localization are still undecided. Demonstration: `Reader.tsx` calls `toastError("Unable to create PDF annotation from this selection.")` for `annotation:selection-error` and for malformed `annotation:create-requested` drafts rejected by the host helper. Critique: this is intentionally generic and does not explain the exact reason (`empty`, `multi-page`, `missing-viewport`, etc.), so it reduces silence but does not yet provide precise recovery guidance. Alternatives rejected or deferred: mapping each reason to static English copy would create more text to replace during localization; hiding feedback until localization is ready would keep the current UX gap; throwing errors would be disruptive and inappropriate for user selection mistakes. Revisit trigger: revisit when localized product copy and per-reason UX guidance are ready.
- Decision: Open the existing header annotation edit popover after explicit header-triggered PDF creation when the user did not request no-editor creation. Why: EPUB annotation creation opens an edit surface before final save, and PDF should match that draft-first interaction while still keeping Thorium as the persistence owner. Demonstration: `Reader.tsx` validates the explicit `highlight:create-from-selection` draft, stores a local `pdfAnnotationDraft`, and passes it to `ReaderHeader.tsx`; `ReaderHeader.tsx` reuses `AnnotationEdit`, saving converts the draft through `pdfAnnotationDraftToNote()` and dispatches the normal note add/update action, while canceling drops the draft without persistence. Critique: this adds a temporary host-side PDF draft path beside the instant/quick persistence path, so tests and docs must keep the two creation modes distinct. Alternatives rejected or deferred: opening the panel edit form after persistence would not match EPUB's pre-save popover; making all PDF creation silent was inconsistent with the normal annotation button's edit expectation; adding a PDF-specific editor component would duplicate `AnnotationEdit` too early. Revisit trigger: revisit if PDF creation gains a richer dedicated annotation editor or if the header popover cannot carry future PDF-specific fields.
- Decision: Keep PDF annotation overlays passive and non-focusable during runtime stabilization. Why: the existing `pointer-events: none` model preserves PDF.js text selection and avoids turning highlights into incomplete interactive controls. Demonstration: overlay tests still assert passive styling, click selection continues through document-level hit-testing, and the harness proves deletion removes the highlight so clicking the old location no longer dispatches selection. Critique: this leaves direct keyboard focus on overlays unresolved and keeps accessibility dependent on the panel focus destination after selection. Alternatives rejected or deferred: making overlays focusable now would require keyboard navigation, ARIA naming, overlap policy, and focus styling; making overlays pointer-interactive would risk breaking PDF text selection; native PDF annotation widgets remain out of scope. Revisit trigger: revisit when a dedicated keyboard-accessible overlay interaction tranche is planned.
- Decision: Expose highlight clickability through a document-level cursor hint instead of making highlight overlays pointer-interactive. Why: the user needs an immediate clickable affordance over PDF highlights, but changing overlay `pointer-events` would re-open the text-selection regression this project deliberately avoided. Demonstration: `PdfAnnotationController` now listens to `pointermove`, reuses the same rendered-geometry hit-test used by click selection, applies a temporary root class that forces `cursor: pointer` over the PDF page, and removes the class on drag, active text selection, geometry changes, and destroy; Jest verifies the cursor hint and confirms highlight elements still use `pointer-events: none`. Critique: this is a visual affordance only, not keyboard accessibility, and it relies on CSS override behavior in the embedded PDF.js document. Alternatives rejected or deferred: setting `cursor` directly on passive highlight elements would not affect the real mouse target; enabling `pointer-events: auto` would risk stealing PDF text selection; a custom floating button would add UI weight outside this UX scope. Revisit trigger: revisit if Electron/PDF.js applies stronger inline cursor rules, if hover cursor flickers over complex text layers, or when keyboard-accessible overlay controls are designed.
- Decision: Let `Shift+click` on a rendered PDF highlight bypass the active-text-selection guard after the highlight hit-test succeeds. Why: PDF.js can leave the original text selection active after creating an annotation, and the explicit edit gesture must still reach the host as `annotation:selected` with `shiftKey: true`. Demonstration: `selectionTargetFromClick()` now resolves the highlight candidate before checking active selection, still ignores simple clicks during active text selection, and Jest covers `Shift+click` dispatch with a leftover selection. Critique: this gives the edit shortcut priority over text-selection preservation only for a confirmed highlight hit; if users expect Shift+click to extend text selection inside a highlighted area, this shortcut takes precedence. Alternatives rejected or deferred: clearing the browser selection automatically after creation would be more intrusive; allowing all clicks through active selection would risk stealing normal PDF selection behavior; making overlays pointer-interactive remains out of scope. Revisit trigger: revisit if user testing shows conflict between Shift+click editing and PDF text-selection extension.
- Decision: Implement PDF instant annotation mode inside the PDF.js webview rather than trying to reuse the EPUB `readerActions.setLocator` saga. Why: PDF selection geometry exists in the PDF.js document, while the EPUB instant mode observes navigator locator state in the parent reader; forcing PDF through that EPUB locator path would invent fake `locatorExtended` data and blur the target model. Demonstration: `ReaderMenu.tsx` forwards the existing `advancedMode` checkbox state through `annotations:set-instant-mode`; `PdfAnnotationController` debounces `selectionchange`, reuses `selectionToDraft()`, deduplicates unchanged selections, dispatches `annotation:create-requested` with `source: "instant-selection"`, and the host persists without opening the editor; Jest covers automatic draft creation, duplicate suppression, and `instant-selection` validation errors. Critique: this keeps instant mode consistent with PDF geometry but still depends on real browser selection behavior inside PDF.js, so Playwright/Electron coverage should eventually exercise it end-to-end. Alternatives rejected or deferred: using the EPUB locator saga would require synthetic EPUB locators for PDF; creating notes directly in the webview would violate Thorium-as-source-of-truth; adding a new persisted reader setting is deferred because the existing EPUB checkbox is local session state. Revisit trigger: revisit if instant mode needs persistence across reader sessions or if PDF.js selectionchange behavior proves noisy in Electron.
- Decision: Keep PDF quick creation as an editor-skip policy for explicit creation, while instant mode is always editor-free. Why: EPUB separates "auto create after select" from "skip editor", but the PDF instant-mode UX requested here is an immediate note-taking flow, not an immediate edit flow. Demonstration: created PDF notes still persist through the same host path; `annotation:create-requested.source` distinguishes instant from explicit creation, `Reader.tsx` also tracks the PDF quick-annotation keyboard shortcut, and `getCreatedPdfAnnotationEditMenuAction()` returns no menu action when `skipEditor` is true. Critique: the naming remains inherited from EPUB and can be confusing because "instant" and "quick" are adjacent concepts; the implementation keeps the policy explicit in the host to avoid hidden webview persistence behavior. Alternatives rejected or deferred: making instant mode open the editor contradicted the requested UX; always skipping the editor for the normal annotation button would diverge from EPUB; introducing new PDF-only options would add UI surface before product copy is settled. Revisit trigger: revisit if UX decides PDF instant mode should have different copy or persistent defaults from EPUB.
- Decision: Map the existing annotation hide checkbox to PDF overlay visibility instead of filtering notes or altering snapshots. Why: `reader.annotations.hide` is a display preference in Thorium, while PDF annotation persistence and panel listing must remain source-of-truth host state. Demonstration: `Reader.tsx` dispatches `annotations:set-visibility` from `annotation_defaultDrawView !== "hide"` on PDF readiness and config changes; `PdfAnnotationController` removes overlay layers when hidden, stores incoming `annotations:sync` snapshots without rendering them, restores overlays from the latest snapshot when visible again, and Jest plus the harness prove hidden highlights cannot be clicked or shown with the pointer cursor. Critique: this hides only webview overlays, so the annotation panel still lists the notes and panel navigation can scroll without a visible flash; that is consistent with EPUB-style hide semantics but may need clearer UX copy later. Alternatives rejected or deferred: deleting or filtering notes would conflate display with persistence; sending an empty `annotations:sync` would lose the webview snapshot and make restoration dependent on another host sync; hiding via CSS alone could leave stale hit-test geometry and cursor hints. Revisit trigger: revisit if product decides the hide checkbox should also filter panel cards, or if print/export/search later need independent visibility policies.
